The five layers, explained

Same architecture everywhere, and the order is the stack: rules → know-how → access → packaging → parallelism. Each layer only earns its place when the one before it isn't enough.

L1InstructionsPersistent rules the agent reads every session▶

A plain markdown file that travels with your project (or lives in your home directory) and gets loaded before the agent starts work. Use it for the rules that apply every time: code conventions, "always run tests before committing," what to never touch. Keep it short — long instruction files get truncated or ignored; push detail into skills instead.

Claude
CLAUDE.md
Hierarchy: home dir → repo root → subdirectory. Custom instructions / Project instructions play this role in claude.ai.
Codex
AGENTS.md
Same hierarchy idea; concatenated with more specific files winning. AGENTS.md is an open standard many other tools now read.
Goose
.goosehints
Plus the instructions: block inside a recipe, which acts as a per-workflow system prompt.
Hermes
SOUL.md
The agent's identity file — first thing in the system prompt (role, tone, boundaries). Hermes also auto-discovers project context files: .hermes.md, AGENTS.md, CLAUDE.md, .cursorrules.
Osaurus
Agent prompts
Configured per agent in-app rather than as a repo file — each agent carries its own system prompt, and the memory system's identity layer plays the persistent-personality role.
Gemini CLI
GEMINI.md
Same pattern as CLAUDE.md, hierarchical from home dir to subdirectory — and it reads AGENTS.md too, so one file can serve both harnesses.
Cursor
Rules
A .cursor/rules/ directory of rule files (successor to the single .cursorrules) — each rule can be always-on, path-scoped, or attached on demand.
OpenCode
AGENTS.md
Uses the open standard directly: repo root for project rules plus a global file for personal ones.
OpenClaw
AGENTS.md + SOUL.md
Workspace instruction files, inheriting the SOUL.md identity-file idea from its Hermes lineage.
Copilot
copilot-instructions.md
Lives in .github/; path-scoped *.instructions.md variants target parts of the repo. The content transfers almost verbatim between all of these files.
L2SkillsReusable know-how, loaded only when relevant▶

A folder containing a SKILL.md file (instructions + YAML frontmatter) plus optional scripts, references, and templates. The key trick is progressive disclosure: the agent sees only each skill's name and description up front, and loads the full instructions only when the task matches. That's why fifty installed skills don't blow up your context window. Skills teach how to do something — a review checklist, a document format, a deployment procedure. They make no network calls and need no credentials.

This is the layer where the ecosystem has genuinely converged: the same SKILL.md format is an open standard (Agent Skills / agentskills.io) shared across vendors, with large cross-harness registries.

Claude
Skills
.claude/skills/ in Claude Code; also in claude.ai, Cowork, and the API. Triggered implicitly by description match.
Codex
Skills
Same SKILL.md standard. ~/.agents/skills/ (personal) or .agents/skills/ (repo). Invoke with $skill-name or implicitly; $skill-installer pulls from registries.
Goose
Skills
Reusable instruction sets attached to sessions; browsable via a skills marketplace, or write your own.
Hermes
Skills
Same format, plus Hermes's signature move: it writes its own skills from experience ("procedural memory") and a background Curator archives stale ones. Huge public Skills Hub; install via hermes skills install.
Osaurus
Skills
A plugin can ship a SKILL.md alongside its tool, so the know-how travels with the capability. Selection is different: skills and tools are picked by RAG search over the task, not by description matching.
Gemini CLI
Skills
Same SKILL.md standard — skills written for Claude or Codex usually run here with little or no change.
Cursor
Skills
Supports the SKILL.md format alongside its own Rules; rules cover the always-on layer, skills the on-demand one.
OpenCode
Skills
Same SKILL.md standard, discovered from project and global skill directories.
OpenClaw
Skills
Same format inside, but distributed as npm packages through the ClawHub registry — install and version them like dependencies.
Copilot
—
No first-class skills layer yet; path-scoped custom instructions cover some of the territory.
L3Tool accessConnections to external systems — all MCP underneath▶

This is where the naming confusion is worst, because every harness gives MCP servers a friendlier product name. An MCP server is a process (local or remote) that publishes callable tools — read email, query a database, create a Jira ticket — over a standard protocol. Unlike skills, these do reach external systems, use real credentials (usually OAuth acting as you), and consume meaningful context per connected server. Install only what you use.

Claude
Connectors
Anthropic's packaging of remote MCP servers inside the Claude apps (Gmail, Drive, Slack…), one-click OAuth. In Claude Code you configure MCP servers directly.
Codex
MCP servers
Configured in config.toml, or bundled inside plugins. The ChatGPT side calls the consumer-facing versions "apps."
Goose
Extensions
Goose's entire tool system: every extension is literally an MCP server, built-in or external. Fully swappable.
Hermes
MCP + Plugins
Native MCP support (hermes mcp, OAuth for remote servers). Separately, "plugins" are Python files in ~/.hermes/plugins/ that add tools, hooks, memory providers, dashboards, and gateways — a code-extension mechanism, not a bundle.
Osaurus
Plugins + MCP
Native Swift/Rust plugins from a community Tools Registry provide tools locally. Uniquely, Osaurus sits on both sides of MCP: it's a server exposing its tools to any MCP client (Claude Desktop included) and an aggregator pulling in remote servers like GitHub, Linear, and Notion.
Gemini CLI
MCP servers
Configured in settings.json, or shipped inside an extension. A server you set up for one harness works across all of them.
Cursor
MCP servers
Configured in mcp.json, with one-click installs from a directory of popular servers.
OpenCode
MCP servers
Local and remote servers configured in opencode.json.
OpenClaw
Built-in tools + MCP
Ships a built-in tool set; MCP reach is added through plugins rather than native config.
Copilot
MCP servers
MCP client in VS Code and in the async coding agent.
L4BundlesPackage everything above into one installable unit▶

Once you have skills, MCP servers, and commands that work together, bundles let you ship the whole setup as one install — mainly a team-distribution mechanism. If you're working solo, you rarely need this layer: just write skills and add MCP servers directly.

Important asymmetries: Claude and Codex plugins are static packages (install once, contents registered). A Goose recipe is a runnable, parameterized workflow — a bundle and an automation in one. Hermes has no plugin-style bundle at all; the closest analogs are profiles (a saved combination of model + skills + MCPs + identity you can switch between) and installable skill packs. Osaurus collapses two layers into one: its plugin package (a zip containing the tool binary, an optional SKILL.md, and an optional web UI) is simultaneously the code extension and the distribution bundle.

Claude
Plugins
A .claude-plugin/ manifest bundling skills, MCP servers, slash commands, subagents, and hooks. Marketplace + official plugins; surfaces vary (Claude Code, Cowork).
Codex
Plugins
Bundle skills, app mappings, and MCP server config into one package. First-class since early 2026, with a large marketplace of first- and third-party plugins.
Goose
Recipes
Shareable YAML workflow: instructions + prompt + extensions + parameters + sub-recipes. Parameterized like a function; can run on a schedule.
Hermes
Profiles
A profile bundles model choice, skills, MCPs, and identity for a purpose ("research me" vs "ops me"). Skill packs distribute related skills together via the Hub.
Osaurus
Plugin package
One zip carries the tool, its SKILL.md guidance, and a web frontend — capability, know-how, and UI ship as a unit through the Tools Registry.
Gemini CLI
Extensions
Bundle MCP servers, context files, and commands into one install. Note the trap: "extension" means bundle here, not MCP server as in Goose.
Cursor
—
No bundle layer; teams share rules and skills by committing them to the repo.
OpenCode
—
Its "plugins" are JS/TS code extensions that hook the runtime, not distribution bundles.
OpenClaw
—
Same story: plugins are code extensions. Distribution happens at the skill layer, via npm packages.
Copilot
Extensions
Marketplace GitHub Apps that extend Copilot — closer to installable integrations than to a skills-plus-MCP bundle.
L5DelegationSpin up specialized workers, often in parallel▶

Subagents are independent agent instances the main agent can hand tasks to — each with its own context window, and often its own tool access and instructions. Useful for parallelizing (review three files at once) or isolating noisy work (a research subagent digests 50 pages and returns a summary, keeping the main context clean).

Claude
Subagents
Defined as markdown files in .claude/agents/; the main agent delegates via its task tool. Can ship inside plugins.
Codex
Subagents
Specialized agent definitions Codex delegates to; a large third-party ecosystem of agent collections exists.
Goose
Subagents / sub-recipes
Each sub-recipe runs as its own agent in an isolated session with its own extensions and model — sequential or parallel.
Hermes
Subagents
The delegate_task tool spawns children with isolated context, restricted toolsets, and their own terminal sessions; background subagents can fan out in parallel. Built-in cron covers the scheduled/unattended case.
Osaurus
Agents / dispatch
Named agents are first-class (each with its own prompt, memory, and tools), plugins can dispatch background agent tasks with full tool access, and agents can self-schedule their next run — cron-like autonomy without a separate scheduler.
Gemini CLI
—
No first-class subagents; parallel work means scripting multiple CLI invocations yourself.
Cursor
Background agents
Async cloud agents run tasks in parallel with your editor session and hand back diffs.
OpenCode
Agents / modes
Primary agents you switch between, plus subagents they can invoke for isolated work.
OpenClaw
Subagents
Spawns isolated sessions Hermes-style for parallel or contained tasks.
Copilot
Coding agent
Assign it an issue or task; it works asynchronously on GitHub's infrastructure and returns a pull request.

Terminology traps

  • "Plugin" is the most overloaded word in the ecosystem. In Claude and Codex, a plugin is a distribution bundle (skills + MCP + commands). In Hermes, OpenClaw, and OpenCode, a plugin is a code extension — a Python or JS file that adds tools and hooks to the runtime. Osaurus splits the difference: its plugin is a native code extension packaged as a bundle (binary + SKILL.md + UI in one zip). Same word, three different meanings.
  • "Extension" flips meaning too. In Goose, an extension is an MCP server (tool access). In Gemini CLI and Copilot, an extension is a bundle. Check which layer before assuming.
  • "Skills" is the safest word. Nearly everyone means the same SKILL.md open standard. The one wrinkle: Hermes skills can be written by the agent itself, and OpenClaw distributes them as npm packages.
  • "Connector" is mostly Claude-speak for a packaged remote MCP server — though the word shows up generically elsewhere to mean any MCP integration.

The layer underneath: MCP

The Model Context Protocol (open standard, released by Anthropic in Nov 2024) is the shared plumbing for the "tool access" row — a JSON-RPC protocol where a server publishes tools any compatible agent can discover and call. This is why the ecosystem interoperates: a Goose extension, a Claude connector, a Hermes MCP entry, and an MCP server inside a Codex plugin can be the exact same server. Osaurus demonstrates the two-way nature of the standard: it consumes remote MCP servers and exposes its own local tools as an MCP server that other harnesses can connect to — so your Osaurus toolbox can serve Claude Desktop. Skills (SKILL.md / agentskills.io) and instruction files (AGENTS.md) are similarly portable open standards. The names are vendor branding; the files and protocols underneath increasingly are not.

Which one do I need?

Start from what you're trying to change, not from the feature name.
